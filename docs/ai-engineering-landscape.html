The AI engineering landscape

General reference, not specific to GigaWhat, written as of mid-2026. An AI engineer builds applications on top of existing models; an ML engineer trains them. Most of the work is ordinary software engineering with a thin model layer on top. The fastest-moving parts (agent frameworks, coding tools) change month to month, so treat the names below as a snapshot.

What has changed

  1. From chatbots to agents. The typical project used to be a chatbot over documents. Now it is models that call tools, take many steps and work for minutes or hours. Coding agents are the breakout use case.
  2. Context engineering has replaced prompt engineering. The hard part is deciding what goes into the context: retrieved documents, memory, tool results, and how to trim long sessions.
  3. MCP became the standard plug. The Model Context Protocol is now the usual way to connect models to tools and data, supported by all major providers. Agent-to-agent protocols exist but have not caught on to the same degree.
  4. Frameworks are getting thinner. Every provider ships its own agent SDK. LangGraph is the most-used independent orchestrator, and many experienced teams write plain code against the provider SDK.
  5. Evals and tracing are mandatory. "Evals are the new unit tests" is a common line, and production teams trace every model call.
  6. Clouds sell managed agent runtimes. AWS Bedrock AgentCore, Azure AI Foundry Agent Service, Google Vertex AI Agent Engine, Databricks Agent Bricks, Snowflake Cortex Agents.
  7. Open-weight models are a real option. Llama, Qwen, DeepSeek, Mistral, Gemma and OpenAI's gpt-oss are good enough for many tasks, especially cheap high-volume steps or data that can't leave the building.
  8. Cost engineering matters. Route each task to the cheapest model that can handle it, cache prompts, and put a gateway in front of the providers.
  9. RAG matured rather than died. Long context windows didn't replace retrieval. Hybrid search with reranking is the baseline, and agentic retrieval, where the agent decides when and what to search, is growing. Graph RAG stays niche.
  10. Security is the unsolved problem. Prompt injection has no complete fix, so the field relies on limiting what tools can do, sandboxing, and human approval for risky actions. Regulation such as the EU AI Act is phasing in.

Underneath all of it is ordinary software engineering, which is the truly universal part: Python first and TypeScript second, Pydantic, FastAPI, Git, Docker and cloud basics.

Where LangChain sits

  • The best-known framework and the one job ads mention most
  • Also the most criticised, mainly for its layers of abstraction
  • Common senior view: LangGraph is respected for production agents, LangChain is handy for its connectors, and you should understand the raw API underneath either way
  • LangSmith, its tracing product, is used even by teams that don't use LangChain

Where Databricks sits

  • Everywhere in large companies, but as a data platform
  • AI engineers meet it when the company's data already lives there: typical in enterprise, finance, energy and retail
  • Startups rarely use it; Snowflake plays the same role elsewhere

Safe to invest in

  • Python and the providers' own APIs
  • Pydantic and structured output
  • Postgres/pgvector and hybrid retrieval
  • MCP
  • Writing evals and reading traces
  • Prompt-injection awareness; cost and latency trade-offs

Expect churn

  • Which agent framework is in fashion
  • Coding-tool rankings
  • Vector database startups
  • Eval and observability vendors
  • New agent protocols

What employers tend to test: whether you can design what goes into context, build a reliable tool-using agent, prove quality with evals, debug from traces, keep cost under control, and defend against prompt injection. The tool names matter much less than those skills.

Design patterns for AI engineering

General reference, not specific to GigaWhat. Language models have a few awkward properties: they are sometimes wrong, slow, expensive, easily misled by instructions hidden in text, hard to inspect, limited by their context window, and always changing. Each pattern below exists to handle one of these, and most have a direct ancestor in ordinary software engineering.

Calling the model reliably

PatternWhat it isWatch out for
GatewayOne service for every model call: keys, quotas, logging, fallbacks, switching providers (LiteLLM, cloud AI gateways)Without one, every team scatters keys and retry code
Retries + fallbacksBack off on rate limits and errors; fall back to another model or providerRetrying a tool call that changes something can do it twice
Structured outputAsk for JSON matching a schema (usually Pydantic), validate it, retry on failureParsing free text breaks quietly
Pin model versionsUse exact model IDs, never "latest"A silent upgrade changes behaviour; re-run evals before upgrading
StreamingShow tokens as they arriveFeels faster, but structured output can only be validated once complete

Context engineering: what the model sees

PatternWhat it is
RAGRetrieve relevant text, then generate from it; refined with hybrid search, reranking and query rewriting
Just-in-time retrievalGive the agent search tools and let it fetch what it needs, rather than loading everything up front
CompactionSummarise a long session as it nears the context limit and continue from the summary
External memory and notesThe agent writes progress to a file or store and reads it back, instead of holding everything in context
Sub-agentsA focused task runs in a clean context and returns only a summary
Cache-friendly prompt layoutStable content (instructions, tools, documents) first, changing content last, so the provider's prompt cache can reuse it

Workflows and agents

PatternWhat it isUse when
Prompt chainingA fixed sequence of calls, each feeding the nextThe task splits cleanly into steps
RoutingClassify the input, then send it down a specialised pathDifferent inputs need different handling or models
ParallelisationRun sub-tasks at once, or ask several times and voteYou want speed or more confidence
Orchestrator–workersOne model plans and hands sub-tasks to workersThe sub-tasks can't be known in advance
Evaluator–optimiserGenerate, critique, reviseThere are clear quality criteria
Agent loopThe model calls tools in a loop until doneThe task is open-ended; always cap steps, tokens and cost
Human-in-the-loopPause for approval before consequential actionsMoney, safety or anything irreversible is involved
Durable executionSave state after each step so a run can resume after a crash or a pause (LangGraph checkpoints, Temporal)Runs are long or wait on people

The first six come from Anthropic's "Building effective agents". The usual advice is to use the simplest pattern that works: a fixed workflow when the steps are known, an autonomous agent only when they are not.

Caching

LayerWhat gets cachedWatch out for
Provider prompt cachingThe repeated start of a prompt (Anthropic, OpenAI, Gemini; vLLM for open models)Large, easy savings, but only if the start of the prompt is identical byte for byte
Exact response cacheSame model, prompt and settings → the stored answerInvalidate it when the prompt, model or source documents change
Semantic cacheQuestions similar to earlier ones, matched by embedding similaritySimilar questions can need different answers; keep it to FAQ-style content, never personalised or permission-restricted answers
Embedding cacheVectors keyed by a hash of the contentSaves re-embedding text that hasn't changed
Tool and retrieval cacheResults of expensive lookupsStale data, and results leaking between users

Observability

PatternWhat it is
Trace everything as spansEvery model call, retrieval and tool call records inputs, outputs, tokens, latency, cost, model version and prompt version; OpenTelemetry has emerging GenAI conventions
One trace ID per requestFollow user → agent steps → tool calls end to end
Cost attributionTokens and spend per user, feature and prompt version
Capture feedbackRatings, edits and accept/reject signals attached to the trace
Redact before loggingStrip personal data before traces leave the app
Watch quality onlineDashboards and alerts on error, refusal and abstention rates and latency, not only uptime

Quality and evals

PatternWhat it is
Golden test setReal questions with expected answers or sources; the base for everything else
Error analysis firstRead 50–100 real traces and group the failures before choosing what to measure
LLM-as-judgeA model scores answers; check its scores against human judgement before trusting it
Regression evals in CIPrompt and model changes must pass the test set before they ship
Online evalsScore a sample of live traffic continuously
Self-verificationCheck grounding and that citations match their sources, in code where possible
AbstainSay "I don't know" when the evidence is below a threshold
Data flywheelFailures found in production become new test cases

Cost and latency

PatternWhat it is
Model cascadeTry a small, cheap model first; escalate to a larger one only when needed
Batch APIsSend offline jobs in bulk, typically at about half price
Cap output tokensOutput costs more and takes longer than input
Parallel tool callsRun independent calls at the same time
Distil or fine-tuneMove a stable, high-volume task to a smaller model
Budgets per runLimits on steps, tokens and money, with circuit breakers to stop runaway agents

Security

PatternWhat it is
Guardrail sandwichCheck the input, call the model, check the output
Least-privilege toolsRead-only by default, allow-lists, narrowly scoped credentials
Avoid the lethal trifectaNever give one agent private data, untrusted content and a way to send data out all at once; together they let prompt injection steal data (Simon Willison)
Quarantine untrusted contentText from documents, web pages and tool results is data, never instructions; in the dual-LLM pattern the model that can act never reads untrusted text directly
Sandbox code executionRun model-written code in an isolated environment
Permission-aware retrievalFilter what the user may see at the data layer, before the model sees anything

Shipping and change

PatternWhat it is
Prompts as codeVersioned, reviewed and tested with evals like any other change
Shadow and canary releasesRun a new prompt or model in shadow mode first, then release it to a small share of traffic, behind feature flags
Defensive UXShow sources, allow edit and undo, set expectations, make feedback easy

Ten to learn first: structured output; a gateway with retries and fallbacks; RAG with hybrid search and reranking; routing; human-in-the-loop; prompt caching; tracing; a golden test set with CI evals; least-privilege tools; the lethal trifecta.
